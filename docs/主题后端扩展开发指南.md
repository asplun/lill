# lill 主题后端扩展开发指南

> 面向第三方主题作者。约定：**主题私有的后端逻辑（自定义接口、短代码、页面模板数据）全部住在主题目录里，core 不含任何具体主题实现。**
> 换主题时把主题目录整个丢进 `frontend/themes/`，core 一行都不用改。

---

## 0. 为什么需要它

Typecho / WordPress 的主题是 PHP，可以直接写 `functions.php`、注册接口、改写输出。
lill 是前后端分离的（后端 Node.js + SQLite，前端模板是纯 HTML + 标签），模板本身不能查库。
于是约定一个 **主题后端扩展入口**，让主题自带一份 Node.js 模块，承担 Typecho 里 `functions.php` 的角色：

- 注册主题私有 REST 接口（说说 / 相册 / 友链 / 番剧 …）
- 输出时转换正文（短代码，例如回复可见）
- 给自定义页面模板注入数据
- 定义后台「小组件」的类型与分组

---

## 1. 目录结构

```
frontend/themes/<主题id>/
├─ theme.json          # 主题元数据 + 设置项（必填）
├─ *.html              # 模板（必填）
├─ style.css
├─ assets/             # 静态资源，nginx 直接托管 /themes/<id>/assets/**
├─ cache/              # 运行时缓存目录（可选，由主题自己写）
└─ backend/            # ← 主题后端扩展（可选）
   ├─ index.js         # 唯一入口，core 只认这一个文件
   ├─ core.js          # 桥接 core 通用模块（见第 5 节）
   └─ lib/             # 主题私有的实现，随便拆
```

**没有 `backend/index.js` 的主题（例如纯展示主题）完全合法**，core 的通用功能不受影响。

---

## 2. 入口文件契约

`frontend/themes/<id>/backend/index.js` 是一个 ES Module，可导出以下成员（全部可选）：

| 导出 | 类型 | 作用 |
|---|---|---|
| `register(router, ctx)` | `function` | 注册主题私有 REST 接口 |
| `transformContent(html, info)` | `async function` | 正文输出钩子（短代码等） |
| `pageTemplate(key, info)` | `async function` | 自定义页面模板的数据注入 |
| `decorateWidgets(rawList)` | `function` | 侧边栏小组件归一化 / 附加 name·icon·group |
| `widgetDefinitions` | `object` | 后台小组件类型定义（`{ type: {name, icon, group, ...} }`） |
| `widgetOrder` | `string[]` | 小组件在后台下拉里的排序 |
| `widgetGroups` | `object` | 小组件分组元信息 |

最小示例：

```js
// frontend/themes/mini/backend/index.js
export function register(router, ctx) {
  router.route('GET', '/api/v1/mini/ping', async (req, res) => {
    ctx.json(res, { pong: true, theme: 'mini' });
  });
}
```

## 3. 生命周期与作用域（重点）

- **启动扫描**：core 启动时扫描 `frontend/themes/*/backend/index.js`，逐个 `import` 并调用 `register`。
- **按激活主题生效**：扩展注册的接口会被 core 包一层——**只有该主题是当前激活主题时才生效**，否则统一返回 `404 {"message":"API 不存在"}`。
  当前激活主题从数据库 `themes` 表 `active = 1` 的行读取。
- **切换主题立即生效、无需重启**：激活判定是**每次请求**实时读取的，所以在后台切换主题后，旧主题的私有接口立刻 404、新主题的接口立刻可用。
- **多主题共存**：多个主题各自带 `backend/`，互不覆盖（不是后注册覆盖前注册，而是按激活态分流）。
- **故障隔离**：`transformContent` / `pageTemplate` / `decorateWidgets` 钩子内部抛错会被 core 捕获并降级（打印告警，不 500），主题写错不会拖垮整站。

## 4. 钩子详解

### 4.1 `register(router, ctx)`

`router` 是 **被 core 包装过的路由器**，只暴露一个方法：

```js
router.route(method, path, handler, requireAuth?)
```

- `method`：`'GET' | 'POST' | 'PUT' | 'DELETE'`
- `path`：以 `/api/v1/` 开头的完整路径
- `handler(req, res, params)`：`params` 是路径里的 `:xxx` 参数
- `requireAuth`：`true` 时该接口需要登录态（core 会先鉴权）

`ctx` 提供 core 的通用能力，常用字段：

| 字段 | 说明 |
|---|---|
| `ctx.db` | SQLite 连接（`node:sqlite` 的 `DatabaseSync`），可用 `prepare(...).get/all/run` |
| `ctx.json(res, data, status?)` / `ctx.error(res, msg, status?)` | 统一 JSON 响应 |
| `ctx.parseBody(req)` | 读取并解析请求体 |
| `ctx.authenticate(req)` | 取当前登录用户（无则抛错） |
| `ctx.uid()` / `ctx.slugify(s)` / `ctx.renderMD(md)` / `ctx.plainText(html)` | 工具函数 |
| `ctx.settings` / `ctx.security` / `ctx.mail` / `ctx.imageHost` / `ctx.feed` | core 子系统 |
| `ctx.UPLOAD_DIR` / `ctx.THEMES_DIR` | 关键目录 |
| `ctx.themeExt` | `{ ids(), get(id), activeId(), active() }`，用于查询主题扩展状态 |

> 约定：主题私有接口一律挂到 `/api/v1/<主题或功能命名空间>/...`，避免和 core 的 `/api/v1/posts`、`/api/v1/comments` 等冲突。

### 4.2 `transformContent(html, info)`

**正文输出钩子**，在文章 / 页面渲染时对 `html_content` 调用一次。

```js
export async function transformContent(html, info) {
  const { req, post, viewer, db } = info;
  // viewer: { user, mail, hasCommented, reveal }  ← core 提供的通用访客上下文
  // 返回字符串则替换输出；返回 undefined 保持原样
  return html.replace(/\[hide\]([\s\S]*?)\[\/hide\]/g, (m, body) =>
    viewer.reveal ? body : '<div class="need-reply">回复可见</div>');
}
```

- 典型用途：`{music}` / `[hide]` 这类短代码。
- **必须按访客身份实时转换**，不要保存时固化（否则所有人看到的内容一样）。
- `viewer.reveal` 表示「已登录或在该内容下留过言」，具体语义由 core 提供，主题直接用即可。

### 4.3 `pageTemplate(key, info)`

**自定义页面模板的数据注入**，当某个独立页面选中了 `page-*.html` 模板时调用。

```js
export async function pageTemplate(key, info) {
  const { db, url, data, pageView, post } = info;
  if (key === 'page-links') {
    data.links = db.prepare("SELECT * FROM links WHERE status='published'").all();
  }
}
```

- 往 `data` 上挂的属性，模板里用 `{$data.links}` 读取（见主题开发指南第 5 节）。
- `key` 是模板文件名去掉 `.html` 后缀，例如 `page-links`。
- 模板下拉的选项来自主题目录里的 `page-*.html`，core 只负责把 `key` 传给你。

### 4.4 `decorateWidgets(rawList)`

侧边栏小组件在配置里是精简结构，渲染前会过一次这个钩子，用来补全展示信息：

```js
export function decorateWidgets(list) {
  return (Array.isArray(list) ? list : []).map(w => ({
    ...w, name: DEFS[w.type]?.name || w.type, icon: DEFS[w.type]?.icon || '',
  }));
}
```

## 5. 桥接 core 通用模块（core.js）

主题扩展可以依赖 core 里**与具体主题无关**的通用能力，但**不能** `import` core 的私有实现。
推荐在主题里放一个 `core.js` 做桥：

```js
// frontend/themes/<id>/backend/core.js
export {
  themeOpt, themeSwitch, themeContext, themeCacheDir, themeCacheUrl, readManifest,
} from '../../../../backend/lib/theme-options.js';
export { shapeComment, orderBy, avatarOf } from '../../../../backend/lib/comment-util.js';
export { clientIp } from '../../../../backend/lib/http.js';
```

core 当前提供的通用模块（`backend/lib/`）：

| 模块 | 用途 |
|---|---|
| `theme-options.js` | 主题配置读取（`themeOpt/themeSwitch/themeRange/themeContext/themeCacheDir/themeCacheUrl`）、`readManifest` |
| `comment-util.js` | 评论整形、头像、排序、树构建 |
| `http.js` | `clientIp` 等 HTTP 小工具 |
| `utils.js` / `security.js` / `mail.js` / `image-hosting.js` | 通用工具与子系统 |

> 路径 `../../../../backend/lib/*` 是相对 `frontend/themes/<id>/backend/core.js` 的默认布局。
> 主题目录与 backend 同级部署时，core 与主题的相对位置是固定的，不要写死绝对路径。

---

## 6. 打包与发布

第三方主题 = **一个自包含目录**：

1. 主题目录里放齐 `theme.json` + 模板 + `assets/` + `backend/`。
2. 打包成 ZIP（根目录含 `theme.json`）。
3. 用户后台「外观 → 安装主题 → 上传 ZIP」安装，或手动拷进 `frontend/themes/` 后重启后端。
4. 安装后主题的 `backend/` 会在下次后端启动时自动加载；启用即生效。

> 主题的 `backend/` 属于主题资产，**不进 core 仓库**，core 里不应出现任何具体主题的名字。

---

## 7. 调试

- 启动日志会打印：`✓ 主题扩展已加载：<id>`；加载失败会打印 `✗ 主题扩展加载失败：<id> — <原因>`。
- 主题私有接口返回 `404 API 不存在` → 检查当前激活主题是否是本主题（切主题后立即变化）。
- `transformContent` / `pageTemplate` 报错不会 500，但会在日志里出现 `theme hook xxx failed: ...`，据此定位。
- 想验证扩展语法：`node --check frontend/themes/<id>/backend/index.js`。
