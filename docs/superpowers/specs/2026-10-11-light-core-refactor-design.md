# lill 轻核心架构重构设计

**日期：** 2026-10-11  
**范围：** 后端职责拆分与可选能力隔离

## 目标

在不改变现有 API、数据库兼容性、Astro 前端、默认主题、TriM3 第三方主题和插件协议的前提下，降低 lill 核心代码的耦合度和维护成本。

这次重构首先做“职责拆分”，不借机重写业务、不更换技术栈、不删除已有功能。

## 现状问题

- `backend/server.js` 同时承担数据库初始化、迁移、认证、路由装配、插件和主题加载、HTTP 中间件以及服务启动。
- `backend/routes/admin.js` 集中处理文章、页面、分类、标签、评论、媒体、用户、设置、主题、插件、备份、日志和系统接口。
- 邮件、反垃圾、图片托管、监控、备份和在线主题编辑器等可选能力与博客核心请求路径耦合。
- 路由处理器直接混合参数校验、权限判断、SQL 写入、文件操作和响应组装，难以独立测试。

## 设计原则

1. **先拆文件，后改实现。** 第一阶段只移动代码和统一注册入口，保持请求行为不变。
2. **API 兼容优先。** 保留现有 `/api/v1/*` 路径、HTTP 方法、响应包结构 `{ code, message, data }` 和主题/插件可用的运行时接口。
3. **核心轻量化。** 核心只保留博客运行所必需的能力；可选能力通过服务模块或插件加载，不在核心路由中互相依赖。
4. **显式依赖。** 模块通过 `ctx` 或明确的服务对象获得依赖，不读取未声明的全局状态。
5. **安全行为不回退。** 保留当前用户状态实时认证、角色权限、资源归属、公开内容隔离和 CSRF 处理。
6. **不触碰现有数据。** 重构期间不打开、迁移或修改 `backend/data/lill.db` 和根目录 `data/`。
7. **第三方主题隔离。** TriM3 只通过现有公开主题协议工作，核心不加入其专用业务判断。

## 目标结构

```text
backend/
  server.js                  启动、配置、HTTP 请求分发
  db/
    schema.js                核心表结构和幂等迁移
  routes/
    admin/index.js            管理路由统一注册
    admin/content.js          文章、页面、批量操作
    admin/taxonomy.js         分类、标签
    admin/comments.js         评论和评论批量操作
    admin/media.js            媒体上传和管理
    admin/users.js             用户管理
    admin/settings.js         基本设置和主题设置
    admin/extensions.js       主题、插件、小工具
    admin/system.js           日志、备份、系统信息
    public.js                 公开接口
    auth.js                   登录和当前用户
    install.js                首次安装
  services/
    auth-service.js           当前用户、令牌和角色辅助
    content-service.js        文章、页面和归属辅助
    media-service.js           媒体文件和上传辅助
    extension-service.js      主题、插件和小工具辅助
    settings-service.js       站点和主题配置辅助
  lib/                        无业务或通用基础设施
```

第一阶段允许 `db/schema.js` 和 `services/` 先不完整建立。不能为了达到目录形状而制造空壳抽象；每个新文件必须承载明确的已有职责，并有对应测试。

## 模块边界

### `server.js`

只负责：

- 读取环境配置并创建 HTTP 服务。
- 创建核心数据库和基础运行时依赖。
- 设置 CORS、安全响应头、请求超时、上传静态读取和异常边界。
- 创建兼容的 `ctx`，注册公开、认证、安装和后台模块。

不再新增具体文章、评论、用户或主题业务。

### `routes/admin/index.js`

只负责按固定顺序调用后台模块的 `register(router, ctx)`。它是后台路由的唯一装配入口，不直接实现业务。

### 后台功能模块

每个模块保留现有路径和处理器行为，仅拥有对应资源的路由。跨模块调用通过 `ctx` 中的服务或小型共享辅助函数完成，不通过循环导入访问其他路由文件。

推荐拆分：

- `content.js`：`posts`、`pages`、`page-templates`、文章批量操作、最近文章。
- `taxonomy.js`：`categories`、`tags`。
- `comments.js`：后台评论列表、导出、状态、回复、编辑、删除和批量状态。
- `media.js`：上传、列表和删除。
- `users.js`：用户列表、创建、更新和删除。
- `settings.js`：站点选项、主题列表、主题激活和主题配置。
- `extensions.js`：主题文件编辑、插件、插件菜单和小工具。
- `system.js`：日志、备份、系统状态、统计和单站点信息。

## 可选能力隔离

第一阶段不删除或禁用现有功能，只建立边界：

- `mail`、`security`、`imageHost`、`feed`、主题扩展和插件运行时继续通过 `ctx` 注入。
- 没有请求使用某个可选服务时，不新增额外初始化或数据库查询。
- 第二阶段才评估将邮件、AI 反垃圾、图片托管、监控、在线主题编辑器和自动备份迁移为独立扩展。
- 任何迁移都必须保留旧 API，或提供兼容适配层后再切换。

## 数据流

```text
HTTP 请求
  -> server.js 通用边界
  -> router 匹配和认证/角色策略
  -> 对应 admin/* 或 public/auth/install 路由模块
  -> service / db / extension runtime
  -> 统一 JSON 响应
```

路由模块不应通过字符串拼接构造不受控的表名或文件路径。现有安全校验在移动时必须原样保留；只有测试证明行为等价后才允许整理。

## 兼容性要求

- Astro 管理后台无需更改调用路径。
- 默认主题和 TriM3 的 bootstrap 数据结构保持兼容。
- 插件继续使用 `ctx.route`、hook、后台菜单和配置接口。
- 主题后端扩展继续使用激活主题范围和现有 `register` 协议。
- SQLite 表结构和已有数据不做破坏性变更。
- 既有错误状态码和 JSON envelope 不因文件拆分改变。

## 分阶段实施

### 阶段一：无行为变化的路由拆分

先创建 `routes/admin/`，逐组迁移后台注册代码；`admin/index.js` 统一注册。每组迁移后运行全量测试、语法检查和路由覆盖测试。完成后删除旧 `routes/admin.js`，但只在所有测试通过后进行。

### 阶段二：基础服务抽取

从已拆分的路由中抽取重复且稳定的逻辑：当前用户辅助、文章归属判断、媒体文件操作、主题配置解析。每个服务提供小而明确的函数，路由只保留输入、调用和响应。

### 阶段三：可选能力边界

评估邮件、反垃圾、图片托管、备份、监控和在线编辑器的实际使用情况。只把确实不属于核心的能力迁移为独立扩展；不为目录整齐而抽象。

## 验收标准

- 全量后端测试通过，现有测试数量不减少。
- 新增路由注册覆盖测试，确认所有原 `/api/v1/admin/*` 路径仍存在。
- 文章、页面、分类、标签、评论、媒体、用户、设置、主题、插件、备份和日志接口的 HTTP 方法与路径不变。
- 公开内容隔离、实时账号状态、角色权限、资源归属和批量原子拒绝测试继续通过。
- Astro 前端、默认主题、TriM3 主题和 Hello World 插件回归测试继续通过。
- `server.js` 不再新增业务路由实现；后台资源逻辑不再集中在单个文件。
- 不改变数据库文件、线上环境或部署配置。

## 明确不做

- 不切换 Node、SQLite、Astro 或原生 HTTP 技术栈。
- 不把 Astro 和后端重新合并。
- 不重写后台 UI。
- 不删除 Typecho/WP 对应的基础功能。
- 不把 TriM3 改成默认主题。
- 不在本阶段新增复杂功能或第三方运行时依赖。
