# lill 核心与第三方主题隔离设计

**日期：** 2026-10-12  
**状态：** 待用户审阅  
**范围：** 将第三方 trim3 从 lill 核心架构中完全解耦，同时保持 Astro 前端、Node.js + SQLite 后端、现有数据和现有主题兼容能力。

## 1. 背景与问题

lill 的目标是一个前后端分离的轻量博客系统：核心提供通用博客能力，主题负责展示和个性化，插件负责可选业务能力。当前代码虽然已经存在主题扩展加载器，但 `backend/routes/public.js`、多个 `backend/lib/*` 模块、部署脚本和核心测试仍直接包含 trim3 的业务判断或历史命名。

这会造成四个问题：

1. 安装或开发一个新主题时，必须理解 trim3 的数据字段、接口和配置，而不是只实现 lill 的通用主题协议。
2. 默认主题和第三方主题的边界不清楚，核心启动、公开 API 和主题切换容易被某个主题的业务影响。
3. trim3 不在核心 Git 跟踪范围内时，核心测试和部署仍然引用它，导致全新克隆、升级和 CI 不稳定。
4. 后续维护会继续把“某个主题需要的功能”误加到核心，核心越来越臃肿。

本设计不是更换技术栈，也不是重写后台；它只修正职责边界和兼容层位置。

## 2. 目标与非目标

### 2.1 目标

- lill 核心源码不依赖、也不识别 `trim3` 或 `TriM3` 主题名称。
- 核心只提供通用文章、独立页面、分类、标签、评论、媒体、用户、设置、认证、主题运行时和插件接口。
- trim3 的菜单解析、说说、相册、音乐、豆瓣、番剧、天气、小组件、图床兼容、主题专用评论接口和模板数据全部由 trim3 主题包自己提供。
- 主题包可以声明自己的设置、页面模板、后端路由、钩子和数据库迁移；切换主题不会修改核心代码。
- 保持 Node.js + SQLite + 原生 HTTP 后端和 Astro 前端不变，继续前后端分离。
- 保持现有核心 API、数据库表和 trim3 用户数据兼容；迁移期间不删除数据，不要求用户重新安装。
- 核心测试不依赖本地存在的 trim3 文件；trim3 回归测试随 trim3 主题包运行。
- 部署流程不写死具体第三方主题，也不允许 Nginx 将通用资源 alias 到某个主题。

### 2.2 非目标

- 不在本次设计中重写 Astro 管理后台或主题模板引擎。
- 不把 trim3 改成 lill 默认主题。
- 不删除 trim3 的功能，不改变 trim3 的视觉设计。
- 不引入 Strapi、Next.js、PHP 或新的运行时依赖。
- 不在没有数据迁移脚本和回滚方案的情况下删除旧表、旧字段或旧 API。
- 不把所有可选能力都强行塞进插件；先建立稳定边界，再按实际使用情况迁移。

## 3. 目标架构

```text
lill 核心仓库
├── backend/
│   ├── routes/                 通用 REST API
│   ├── services/               文章、评论、媒体、设置等通用服务
│   ├── lib/theme-runtime.js    通用主题加载、设置、钩子和路由隔离
│   ├── lib/plugin-runtime.js   通用插件加载和生命周期
│   └── test/                   只测试核心契约和默认主题
├── frontend/themes/default/    lill 官方默认主题
└── docs/                       核心 API 与主题/插件协议

独立第三方主题包
└── trim3/
    ├── theme.json
    ├── templates/ 或主题模板文件
    ├── assets/
    ├── backend/
    │   ├── index.js            主题扩展入口
    │   ├── routes/              主题私有接口
    │   ├── services/            主题私有业务
    │   ├── migrations/         主题私有表的幂等迁移
    │   └── compatibility/       历史 trim3 API 兼容层
    └── tests/                  trim3 自己的回归测试
```

仓库形态可以分两步实施：第一步允许 trim3 仍作为服务器上的独立主题目录安装，以降低迁移风险；第二步再把该目录拆成独立 Git 仓库或 release 包。无论仓库是否分开，代码依赖边界必须先分开。

### 3.1 核心允许知道什么

核心只通过主题清单和通用运行时了解主题：

- `id`、`name`、`version`、`author`、`description`；
- 模板和主题资源是否存在；
- 页面模板的通用声明；
- 设置字段的 `key`、`type`、`default`、`options`、`private`；
- 后端扩展入口及其协议版本；
- 主题扩展注册的路由、钩子和视图数据。

核心禁止出现以下主题业务概念或专用判断：

- `trim3`、`TriM3` 主题名；
- `moments`、`albums`、`music_playlists`、豆瓣、番剧等主题专用业务；
- `tri_*` 配置函数语义、trim3 菜单格式、trim3 Cookie 名；
- “如果当前主题是某主题”的分支；
- 只为某个主题保留的公开 API 路径或模板 key。

## 4. 通用主题运行时协议

现有 `backend/lib/theme-ext.js` 作为过渡基础，重构为通用主题运行时。协议采用能力探测，不以主题名称判断行为。

### 4.1 `theme.json`

主题清单增加明确的通用字段：

```json
{
  "id": "example-theme",
  "name": "示例主题",
  "version": "1.0.0",
  "engine": "lill-template-v1",
  "backend": {
    "entry": "backend/index.js",
    "protocol": 1
  },
  "templates": [
    { "file": "page-links.html", "name": "友情链接" }
  ],
  "settings": [
    {
      "key": "accentColor",
      "label": "强调色",
      "type": "color",
      "default": "#6750a4",
      "private": false
    },
    {
      "key": "providerToken",
      "label": "服务令牌",
      "type": "text",
      "default": "",
      "private": true
    }
  ]
}
```

`private: true` 是通用安全属性。核心根据 manifest 过滤主题配置，不再维护某个主题的私有键白名单。

### 4.2 扩展入口

主题扩展只依赖运行时传入的公开上下文，不导入核心路由文件：

```js
export function register(runtime) {
  runtime.routes.add('GET', '/api/v1/themes/example-theme/data', handler);
}

export async function extendBootstrap(view, context) {
  return { ...view, extension: { example: buildData(context) } };
}

export async function extendPageTemplate(view, context) {
  return view;
}

export function migrate(context) {
  // 只创建该主题声明的表，必须幂等
}
```

实际接口名称以实现阶段的协议文件为准，但必须满足以下边界：

- 路由只能通过 `runtime.routes.add()` 注册；核心不代写主题路由。
- 主题扩展只能在自己激活时提供主题私有路由；非激活主题路由返回统一 404。
- 主题只能通过 `context.core` 使用明确列出的核心能力，不能读取核心路由模块的内部变量。
- 扩展返回的主题数据放入主题扩展命名空间；为兼容旧主题，允许由扩展自己执行一次兼容扁平化，核心不实现扁平字段。
- 生命周期失败要记录日志并让核心继续提供通用博客 API；迁移失败不能静默标记成功。

### 4.3 通用 bootstrap 数据

核心公开 bootstrap 只生成所有主题都可能使用的字段：站点信息、当前用户公开状态、文章/页面、分类、标签、评论摘要、分页、永久链接和主题元数据。

主题特有字段由通用钩子产生：

```text
core bootstrap
  -> activeTheme.extendBootstrap(coreView, context)
  -> 返回给 Astro 前端
```

兼容旧 trim3 前端时，trim3 扩展可以在自己的 `extendBootstrap` 中提供现有字段；这不允许核心重新加入 trim3 字段。

## 5. 职责迁移清单

### 5.1 保留在 lill 核心

- 文章、页面、分类、标签及其公开查询；
- 评论、回复、审核、点赞和通用头像策略；
- 用户、角色、认证、CSRF 和权限；
- 本地媒体库和基础上传；
- 站点选项、永久链接和主题设置通用读写；
- 通用主题扫描、主题切换、manifest 校验和页面模板发现；
- 通用插件加载、钩子、后台菜单和插件配置；
- 通用安全校验、限速、日志、备份和健康检查；
- 通用邮件通知接口（配置归入站点/插件配置，不使用主题专用命名）。

### 5.2 移入 trim3 主题包

- trim3 菜单类型、图标自动匹配和旧菜单文本解码；
- 说说、说说评论、相册、音乐、友链增强、豆瓣、番剧；
- 天气、一言、今日诗词和 trim3 小组件定义；
- trim3 专用首页模式、横幅、播放器和局部列表接口；
- trim3 主题模板数据注入和 `page-*` 专用业务模板；
- trim3 历史 API 兼容路径；
- trim3 图床服务适配和历史图床配置转换；
- trim3 主题自己的缓存、外部服务和数据库扩展表。

### 5.3 作为通用可选扩展处理

远程图床、AI 反垃圾、外部天气服务等不属于博客最小核心。迁移时分为两类：

- 仍是通用基础设施的能力，保留通用服务接口，但去掉 trim3 命名和主题配置依赖；
- 仅由 trim3 使用的能力，移入 trim3 扩展或独立插件。

判断标准不是“当前文件在哪”，而是“默认主题和任意普通主题是否需要该能力”。

## 6. 数据库与兼容迁移

### 6.1 表归属

核心稳定表保持不变：

```text
users, posts, post_versions, categories, tags, post_tags,
comments, media, options, logs, themes, plugins
```

trim3 专用表由主题迁移声明负责：

```text
moments, moment_comments, albums, album_photos,
music_playlists, links 以及第三方数据缓存表
```

本次改造不删除现有 trim3 表。trim3 首次激活时检查并补齐自己的表和字段；如果表已经存在，只执行幂等校验，不覆盖用户数据。

### 6.2 历史配置

- 旧的 `themes.config` JSON 原样保留。
- trim3 扩展负责把旧配置映射到新 manifest 字段；核心只提供通用 JSON 读写和类型归一化。
- 私密字段不再由核心硬编码名单判断，而由主题 manifest 的 `private` 属性决定。
- 迁移完成前保留旧键读取能力，保存时可以同时写入新键；确认兼容后再由 trim3 自己停止读取旧键。

### 6.3 历史 API

现有 trim3 调用的旧接口不能在核心中继续保留。兼容接口由 trim3 包注册，并可以继续使用旧路径，以保证旧模板先能运行。兼容路由必须带有迁移注释和测试，后续可以在 trim3 新版本中逐步改为主题命名空间路径。

核心 API 的通用路径不改变，例如文章、页面、分类、标签、评论、媒体、认证和后台管理接口继续保持现有方法、路径、状态码和 `{ code, message, data }` 外壳。

## 7. 前后端分离与主题切换

架构仍然是前后端分离：

```text
Astro 构建产物 / 主题资源
        │ HTTP
        ▼
Node.js lill REST API
        │
        ▼
SQLite
```

主题包不是把前后端重新揉在一起：

- Astro 前端负责页面和交互；
- Node 核心负责通用 API；
- 主题后端扩展只提供该主题需要的 API 和视图数据；
- 主题切换通过运行时选择当前主题，不要求修改核心代码或重启 Node；
- 默认主题没有扩展时，核心只返回通用 bootstrap，仍然可以正常运行。

主题切换流程：

1. 后台校验主题 manifest 和目录完整性。
2. 写入 `themes.active`，保留各主题独立配置。
3. 运行主题的幂等激活迁移；失败则回滚 active 标记。
4. 后续请求由运行时按当前主题调用扩展。
5. 旧主题私有路由立即按 404 处理，避免切换后路由串用。

## 8. 部署与仓库边界

部署脚本必须使用通用主题目录或主题包清单，不出现具体第三方主题名称：

```bash
THEMES_DIRS="frontend/themes/default"
# 或由发布配置显式指定需要部署的主题包
```

要求：

- 核心部署只同步核心构建产物、后端和被选择的主题包；
- 不使用 `--exclude trim3` 这类主题专用判断；
- 服务器上手工维护的第三方主题不被核心发布覆盖，但这是发布清单/版本策略，不写死主题名；
- Nginx 只指向构建根目录的通用资源，不把 `/theme.js` alias 到某个主题；
- trim3 单独发布时可以有自己的安装包、备份和回滚，不影响核心升级。

## 9. 测试策略

### 9.1 lill 核心测试

核心测试只使用默认主题和一个最小 fixture 主题，覆盖：

- manifest 校验、主题扫描和页面模板发现；
- 主题设置默认值、类型转换和私密字段过滤；
- 扩展路由只在激活主题时生效；
- 非激活主题路由返回 404；
- bootstrap 在没有主题扩展时仍能完整返回；
- 任意 fixture 主题可以增加自己的数据而不修改核心；
- 通用文章、页面、评论、媒体、用户和权限 API 回归；
- 全新克隆不需要 trim3 文件即可运行完整核心测试。

### 9.2 trim3 主题测试

trim3 的测试随 trim3 包运行，覆盖：

- trim3 私有表迁移和历史数据兼容；
- trim3 主题设置和敏感配置；
- 说说、相册、音乐、豆瓣、番剧、小组件和旧 API；
- trim3 模板与其 Astro/前台资源；
- trim3 的第三方服务超时、缓存和降级。

核心仓库不再有 `trim3-theme-*.test.js` 这类直接读取第三方目录的测试。

## 10. 分阶段实施

### 阶段一：先建立协议和隔离测试

- 新增通用主题运行时契约和 fixture 主题测试；
- 增加核心源码边界测试，禁止核心依赖具体第三方主题名和私有字段白名单；
- 盘点当前 `public.js` 中所有主题专用逻辑，建立迁移清单；
- 不改变 API、不动数据库数据、不部署线上。

### 阶段二：迁移公开数据和页面模板

- 把公共 bootstrap 中的主题专用菜单、横幅、播放器、页面数据和小组件整理进主题扩展钩子；
- 核心只保留通用 view model；
- trim3 扩展提供兼容扁平字段，保证现有 trim3 前台不需要一次性重写。

### 阶段三：迁移主题私有路由和可选服务

- 将 trim3 私有 API、兼容 API、外部数据源和图床适配迁回主题包；
- 将核心中的主题专用设置读取重命名为通用设置服务；
- 通用邮件、安全和媒体能力保留明确接口，必要时再拆成插件/provider。

### 阶段四：迁移测试、部署和文档

- 把 trim3 回归测试移出核心；
- 移除部署脚本和 Nginx 示例中的具体主题判断；
- 更新 API 文档、主题开发指南、插件指南和部署文档；
- 对核心仓库做全新克隆测试，对 trim3 包做独立安装/升级测试。

每个阶段完成后先运行核心测试和对应主题测试，再进入下一阶段。任何阶段发现兼容问题，优先增加适配层，不直接把主题逻辑加回核心。

## 11. 验收标准

只有全部满足以下条件，才认为架构隔离完成：

1. `backend/` 核心源码、核心测试和核心部署配置不出现 trim3 专用业务判断。
2. 默认主题在没有 trim3 目录时可以启动、安装、登录、发布文章和渲染前台。
3. trim3 作为可选主题安装/卸载时，核心 API 和默认主题不受影响。
4. trim3 私有功能只由 trim3 扩展注册，切换到默认主题后其路由不会继续生效。
5. 现有通用 API、数据库和用户数据保持兼容；历史 trim3 数据由主题迁移读取。
6. 主题设置私密字段由 manifest 声明控制，核心不存在 trim3 字段白名单。
7. 核心测试不读取 `frontend/themes/trim3`，trim3 测试可以在独立包中运行。
8. 部署配置不写死第三方主题目录，Nginx 不 alias 到具体主题资源。
9. Astro 前端与 Node API 仍然独立构建和部署，没有重新合并成单体应用。
10. 全量测试、语法检查、路由快照和全新克隆启动检查均通过。

## 12. 风险与回滚

- **主题扩展迁移不完整：** 先保留兼容适配器，由扩展返回旧前台需要的数据；不在核心里补回专用分支。
- **旧 trim3 数据结构不同：** 主题迁移只新增缺失结构，不删除字段；所有迁移可重复执行。
- **主题切换失败：** active 标记和迁移操作使用明确的失败处理，失败时恢复上一个激活主题。
- **部署覆盖第三方文件：** 发布脚本采用显式主题清单和 dry-run 校验，禁止按主题名称写排除规则。
- **核心 API 变慢：** 主题扩展只在当前主题请求需要时运行，外部网络请求必须有超时、缓存和失败降级；核心通用请求不等待无关主题服务。

本设计批准后，下一步才编写逐任务实施计划；实施前仍需单独确认计划和执行方式。
